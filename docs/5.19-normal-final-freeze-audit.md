## Firmware：primary + fallback

历史证据：`git log --all -G 'prettyversion|/etc/version.txt' -- '*.sh' '*.py' '*.md'`，及 `88164e9:native-reading-time-package/compat/detect_env.sh` 的 `detect_reading_environment()`，显示旧 compatibility 实现先解析 prettyversion，未得到版本才解析 version。`13b6ce1` 才将两个来源合并后要求唯一版本。当前 fixtures 的 `Kindle 5.19.6 (build 519999999)`、CRLF、带引号和 Firmware Version 前缀都是模拟输入；没有找到目标 5.19 Kindle 两文件配对的真实采样，不能用它们证明两文件必然一致。

因此移除缺乏设备证据的跨来源 consensus：

1. `/etc/prettyversion.txt` 可读取且只含一个唯一、完整、纯数字 dotted version，直接使用它；不读取 fallback 来表决。
2. primary 不存在、读取失败或没有可解析版本时，才读取 `/etc/version.txt`。读取的返回值独立检查，不借 pipeline 隐藏 cat 失败。
3. 任一被选中来源内有多个不同版本，立即拒绝。**primary 多版本歧义不能被 fallback 掩盖**；这是用户明确要求的 primary-ambiguous safe reject。完全未使用的 fallback 不影响有效 primary。
4. primary 唯一解析为旧固件或其他版本时，不借 fallback 绕过 gate。只允许 `5.19.<数字 patch>`，允许多个数字 patch 层级，包括 5.19.0、5.19.1、5.19.6、5.19.6.1。重复同值允许；5.17、5.18、5.20、5.190、garbage、附着乱码与畸形 patch 拒绝。

没有新增型号或序列号白名单。原 300 项中的三项跨来源案例保留，但预期随最终规则更正为“有效 primary 优先”；其余旧检查保留。

## BusyBox / POSIX command matrix

实际范围为两文件 bootstrap、internal installer、launcher、runtime-lock、runtime-child、cleanup，以及 payload 内两个 UI shell、原 daemon 和直接调用的 helper。只读检查旧脚本，不更改统计或封面逻辑。

| 命令/语法 | 生产用法 | 审计结论 |
|---|---|---|
| sh | POSIX functions、case、test、read -r、参数展开、算术、trap、wait | sh/dash syntax 与实际控制流执行；无 shell arrays、`[[ ]]`、process substitution |
| mkdir / rmdir | -p；原子 owner 目录与空目录释放 | 不依赖 flock；不递归删除别人的锁 |
| rm / mv / cp / chmod | -f/-rf、普通 mv、cp -p、数字 mode | 标准/BusyBox 支持；故障注入使用真实目录和逐步发布 |
| cat / cmp | 普通 cat、cmp -s | 无 GNU 特有选项；读取失败或比对失败拒绝 |
| grep / sed / awk / tr | grep -q/-E、sed -n 基本表达式、awk -v/-F、POSIX ERE、字符类 | 无 sed -r、gawk 专用 API；awk associative arrays 不属于 shell arrays |
| df | `LC_ALL=C df -Pk` | BusyBox 文档明确列出 -P/-k；组合参数无不兼容证据，保留 |
| du | `du -sk` | BusyBox 支持；不用 du -b |
| tar | `-tf`、`-xf ... -C ...` | 系统 tar 成功即返回；缺失/失败才尝试 busybox tar；均失败即拒绝 |
| cksum | POSIX cksum 从 stdin 读取 | payload、resource manifest、rollback journal 保持 POSIX CRC；不新增 runtime sha256sum |
| kill / sleep | kill -0、针对 owned PID 的 TERM；sleep 整数 | 不使用 killall/pkill；新增服务检查只观察本插件 Upstart PID |
| date | 无参数日志时间；原 daemon/UI 的 +%s 与日历格式 | +%s 是 BusyBox 已有能力；没有 date -d |
| stat | 原 cover helper 的 `-c '%s:%Y'` / `-c '%s'` | 非 POSIX 但 BusyBox 文档支持；已有失败 fallback（present / 0），保持原样 |
| dirname / cd | dirname --、CDPATH= cd --、pwd | BusyBox/ash 支持的 option terminator；绝对部署路径，无 GNU readlink -f/realpath |
| head / tail / sort / wc / unzip | 原 UI 的简单列/行排序与 zip 读取 | 保持基线；无 find -printf/xargs 特殊参数 |
| mkfifo / FD 9 | owned child-start FIFO、9<>、read/write | ash/Linux 支持；FIFO 双向打开属 Linux 行为，sh/dash 实际 handoff 执行，不宣称任意 POSIX OS 保证 |
| Kindle commands | initctl、mntroot、LIPC、fbset、FBInk、Lua | 离线 mock；真正 UI framebuffer、触摸及系统服务行为留给 KPW |

依据：[BusyBox 官方 applet 文档](https://busybox.net/BusyBox.html)、[POSIX df](https://pubs.opengroup.org/onlinepubs/7908799/xcu/df.html)、[BusyBox df 源码](https://raw.githubusercontent.com/brgl/busybox/master/coreutils/df.c)、[dirname 的单参数处理源码](https://raw.githubusercontent.com/brgl/busybox/master/libbb/single_argv.c)。后者明确跳过 `--`；df 用 getopt32 接受 P/k，输出在 -P 时不因设备名长度而折行。BusyBox 编译配置可以裁掉 applet 或 feature，官方支持不能等同于目标 Kindle build 实测。源码参考为 upstream mirror 的 master，不能据此声称已经确认 Kindle 的具体编译版本。

本机 PATH/既有 Git 工具目录未找到 BusyBox，WSL 无已安装发行版；没有联网安装软件。**实际执行 BusyBox ash：0 次**。实际执行的是已有 MSYS sh/dash、host tar/du/cksum 与真实文件部署；busybox tar fallback 的能力分支以 fixture 模拟，底层调用 host tar。command/option audit 是静态检查，不是 100% Kindle portability 证明。

### df / du / tar / cksum

df 两处均保留 `LC_ALL=C df -Pk`。awk 接受 1024-blocks 与 1K-blocks 单位标记，不依赖 Capacity/Use% 等列名；只接受一条完整六字段数据行，严格校验数字、总量/已用/可用与百分比、可用量 >= 预算。额外空白/制表符可接受。filesystem 或 mount 字段带空格、折行、缺列、多设备、错误单位或非数字均安全拒绝，绝不把移位字段当成可用量。命令非零同样拒绝。目标路径均为 /tmp、/mnt/us，不猜测其它设备的布局。

du helper 接受单行非负数字大小（< 1073741824 KiB），检查命令退出值，保留路径含空格的正常输出。空目录大小允许为零，真实 payload 要求 >0。普通/空/缺失目录、命令失败、额外 whitespace、非数字、负数、多行均覆盖。

tar 的系统成功、系统失败、系统缺失、两者失败分支都执行生产函数；`-tf` 与 `-xf ... -C` 均测试。外层 payload 与内层 manifest 仍用 cksum+size；空文件与包含 NUL/非 ASCII 字节的 POSIX CRC 额外与 build 算法对照。SHA-256 仅供本地构建校验。

## Cross-lock 与 acquisition order

确认缺陷：起点 launcher 在 acquire_runtime_lock 前 `. "$RELEASE/bin/runtime-lock.sh"`；同版本 repair 会先移动旧 release，此时 helper 可能暂时不存在。正式 launcher 现在内嵌 canonical runtime-lock.sh，构建与测试严格核对其逐字一致，不在锁前读取 release helper。

launcher 在申请 shared lock 前、申请成功后各检查 bootstrap lock：live owner、安全不可判断的锁/创建者空目录窗口均提示安装正在进行并退出。只有 dead owner 的 private lock 可由 UI 忽略；UI 不删除它，下一次 installer 按既有协议恢复。第二次检查覆盖观察与 shared claim 的交接窗口。若 installer 随后开始，UI 已持有 shared lock，installer 必须拒绝，不能进入 transaction。

| 场景 | 最终行为 |
|---|---|
| UI 已运行 → installer | internal installer 不能取得 shared lock；明确“阅读记录正在运行，请先退出后再安装”；不 stop、不 STAGE/snapshot、不 root_rw、不发布 runtime |
| bootstrap 解包中 → UI | launcher 自带锁代码，在读取 MAIN/系统属性前发现 live install owner，安全返回；installer 不受影响 |
| repair 发布窗口 → UI | 即使旧 release 已移动、当前 release 不存在，仍可执行 formal launcher 的锁代码，安全拒绝 |
| cleanup → 活动 UI | cleanup 不申请 install/shared lock；只删白名单安装残留，UI/reader、runtime 与 shared lock 保留 |

实际顺序：**public install/upgrade/repair：bootstrap private install lock → shared UI/runtime lock → staging/snapshot → transaction**。direct internal installer 只申请 shared lock，然后 transaction；UI 仅申请 shared lock，并观察 private lock，从不持有/申请它；cleanup 不申请任何锁。不存在 shared → private 的反向 acquisition，也没有等待另一个锁的循环：竞争时直接拒绝。

INT/TERM/HUP 清理保持 owned child handoff → wait → release shared/private；空锁、dead owner、legacy PID、reaper 竞态与 signal owner gap 继续保留原回归。新增 actual launcher/installer 双向场景、repair release 缺失窗口、cleanup+UI、dead installer owner 与三信号 handoff 检查。

## Rootfs/service rollback 与 PID 验证

没有新增 rootfs 空间计算。确认的缺口是原 stop_daemon 只验证 Upstart stop/waiting，未检查此前报告的实际 PID；此外 activation/rollback 的 status | grep 会掩盖 status 非零退出。新增仅解析精确 `native-reading-time start/running, process <正整数>` 的 helper，记录本插件 Upstart 报告的 PID；stop 后同时要求 stop/waiting 与该 PID 不再存活。任何异常/仍存活，拒绝发布和覆盖。不会按名字杀进程，不会终止任何未明确拥有的系统 PID。

activation 和旧服务恢复分别检查 status 命令成功、正确 job/running 状态及其 PID 存活；输出 running 但 exit 非零也不能成功。已有 daemon/tracker/service 配置本体不改。

| 故障注入 | 必须验证的结果 |
|---|---|
| root remount rw 失败 | snapshot 完成后拒绝，旧 runtime/服务未发布、daemon 未停，root_ro 收尾 |
| rootfs target 只读 / service conf copy 失败 | 发布中止，撤回新 runtime，恢复旧 service/部署文件、旧 daemon |
| 新 runtime 已发布但 service 尚未成功 | 完整旧版本恢复；不记录 SUCCESS |
| service 已发布、reload/start/status/activation cmp 失败 | rollback 恢复旧 runtime+service；校验成功才恢复旧 daemon |
| stop 非零 / stop exit 0、实际 PID 仍活着 | 不覆盖；rollback 无法确认停止时保留 snapshot，RECOVERY_REQUIRED |
| rollback restart 失败 | 旧文件已恢复仍不能记成功；保留 journal/backup 并报告 RECOVERY_REQUIRED |
| 已停止 job 的 stop 非零 | 只有 stop 前/后均确认 waiting、此前 owned PID 已消失时才可继续恢复；不把 inactive-job 非零误当存活 |
| 新 activation 报 running 但 PID 不存在 | 不能记成功；rollback 恢复旧文件与旧服务 |
| 同 PID 的旧 snapshot 路径撞名 | mkdir 失败不授予所有权；finish 不删除之前的 journal/backup |

起点缺陷已用真实 owned sleep PID 复现：原生产 stop_daemon 返回 0，但该 PID 仍存活，记录见本地 `build/validation/freeze-stop-defect.log`。新增回归模拟 service stop 返回成功且 status 声称 stop/waiting，但真实 PID 仍存活；确认 installer 不覆盖、不杀该 PID，保留恢复快照。测试结束仅由 fixture 终止其创建的进程。其余 service PID 123 是明确 mock，不能作为真实 daemon 证据。

另两项缺陷用生产事务复现并最小修复：新服务 start 失败、job 已 waiting 且旧 PID 消失时，后续 stop 非零原本仍阻止恢复（`build/validation/freeze-inactive-stop-defect.log`）；STAGE 路径已经存在而 mkdir 失败时，finish 原本会删除不属于本次事务的旧 snapshot（`build/validation/freeze-stage-collision-defect.log`）。前者保留前/后状态和 PID 核验，后者增加 STAGE_OWNED，只有本次 mkdir 成功才允许常规清理。新 PID parser 也拒绝其它 job、多行状态、零/负数及附着内容，不借最后一个 process 字段选择 PID。

既有 journal cksum/记录数、缺 backup 拒绝、old-release 受检删除再 move、rollback reload/root_ro/start 错误处理均保留。文件恢复不完整时不启动混合 runtime。**RECOVERY_REQUIRED 路径必须继续存在**：保留 `/mnt/us/reading-time/.install-9.7.6-normal.<PID>`、journal 和尚存 backup/old-release，退出非零，绝不删除唯一恢复材料。新增 repair 故障矩阵给 prior UI/daemon/service fixture 增加无害注释，使旧/新字节明确不同；逐文件比对能实际检出 mixed deployment，不能靠同版本相同文件掩盖恢复缺口。

## 迁移执行顺序

1. 保留当前三个 9.7.6 环境页面、所有 Tag 与原附件；保留 9.7.4、9.7.5、KS 测试页及五个既存草稿。当前不能在“不删除历史页面”的前提下让物理页面总数立即变成一个，迁移后只有 `v9.7.6` 作为规范维护页面，三个旧页面明确作为迁移前存档。
2. 审阅统一正文、来源及附件，再另行授权维护者提交发布工程文件、选择正式基线并创建新 `v9.7.6` Tag。不要推送已有 KS 工作区修改或重写旧 Tag。
3. 显式 `--upload-draft` 创建或续传唯一规范草稿；一次集齐 3 ZIP + SHA256SUMS + 来源清单。上传失败保留旧附件，冲突拒绝，不使用 `--clobber`。
4. 在草稿核对全部实际附件、哈希、标题、安装教程及待完成列表。未来公开前须另行授权；本轮没有执行公开命令，不能把模拟上传测试描述为远端已上传验证。
5. 正式公开后再把其设为 latest；此后 README 的 `/releases/latest` 自动指向规范页面。为三个旧 9.7.6 页面增加统一页入口，保留全文、原文件名、下载 URL 和 Tag。下面是可添加的提示，**本轮未写入 GitHub**。

> 此页面为 9.7.6 的历史环境专用发布，原安装资源继续保留。统一版本及环境选择见 [Kindle 阅读记录 v9.7.6｜多固件兼容版](https://github.com/L-1116/kindle-reading-records-enhanced/releases/tag/v9.7.6)。请按固件、越狱方式和机型选择 Assets。

没有公开统一页时不能先添加可点击但不存在的新入口。已有不可变页若将来存在，保留其附件与 Tag，按 GitHub 允许的说明编辑能力更新入口；不关闭保护来替换资源。新版本继续 `v9.7.7`、`v9.7.8`；新增未验收环境不塞入已公开不可变页面。

| 比较项 | A：Tag 指向旧运行基线 | B：Tag 指向本轮工程提交（建议） |
|---|---|---|
| Standard 运行代码 | 已验收源码 | 同一源码；脚本强制验证保护路径无变化 |
| 从 Tag 找统一发布工具 | 找不到，必须另取工具分支 | 可以；包含脚本、矩阵、测试、CI 和文档 |

| 历史兼容性 | 不移动旧 Tag | 不移动旧 Tag，不修改已验收 ZIP 或运行身份 |
| 用户可能误解 | 容易误以为旧 Tag 包含全部适配及工具 | 说明 Tag 是发布工程树，三个变体仍按清单检出；Source code 仍不是安装包 |

`9.7.6-unified-preview.md` 保留上轮运行基线 A 的已校验预览；方案 B 的最终可发布正文在本地提交后动态生成于 `dist/unified/v9.7.6-release/RELEASE.md`，其中包含实际工程完整 SHA。下一轮上传只使用 B 目录及显式工程 SHA，不误用旧 A 预览。完整本地提交 SHA、最终 staged 文件及 post-commit 结果另写入 `build/unified-release-precommit/final-report.json`，避免向提交文件嵌入自身 SHA。

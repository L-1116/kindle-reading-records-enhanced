# 9.7.5-V3：5.18.1 启动兼容补丁

本补丁依据两个 5.18.1 失败反馈，对第一次全屏刷新增加最小兼容路径。
没有旧设备完整日志，也没有失败设备的真机验证；这是有针对性的兼容尝试，尚不能宣称根因已证实或故障已解决。

## 已审查的实际调用链

`阅读记录-entry.sh` → `launch.sh` → source `compat/detect_env.sh` → 检查整个 `fw518` 家族的 hard-float 环境、依赖、数据和 UI → 优化 UI `阅读记录-optimized.sh`。

优化 UI：`detect_screen()` → `find_touch_device()` → 资源检查 → 设置 `eatTapMode=0` / 禁止休眠 → `build_cache()` → `draw_background()` → `draw_dynamic 1` → `render_daily()` → Lua 合成 PGM、FBInk `-b` 发布图像和文字 → `refresh_region()` → 计算触摸参数 → Lua 打开 input device → 阻塞读取事件 → 返回动作 → 事件循环。

安装器已按原有流程安装环境探测器、launcher 和优化 UI；不需要增加安装步骤。渲染失败仍会进入既有旧版 UI fallback，本补丁不修改该路径。

## 技术判断

- 案例 A 已显示月历，且缺少正常的第二次闪烁：首次 GC16 flashing 提交或设备端的刷新处理是优先嫌疑点。Shell 同步等待 FBInk 命令返回；若命令卡住，则不会启动触摸 Lua。画面可见本身不能证明这一调用已经返回，原生系统也可能参与更新同一 framebuffer。
- 案例 B 白屏但原生菜单可用：符合插件局部启动/显示失败，不支持“整个系统死机”的判断。也可能是绘制、依赖或输入启动失败，不能仅凭白屏锁定刷新驱动。
- FBInk 官方 CLI 将 `-f` 作为强制闪烁请求，`-s` 无区域参数为全屏刷新，`-W` 选择 waveform，`-b` 只写 framebuffer。因此保留 GC16 和全屏范围，只去掉第一次刷新中的 flashing 请求，适合作为可回滚的单变量尝试。[FBInk CLI 源码](https://github.com/NiLuJe/FBInk/blob/master/fbink_cmd.c)
- 当前代码没有传 `-w`。上游文档指出 FBInk 1.20.0 之前会对 flashing updates 自动等待完成，较新版本则可显式等待；失败设备实际使用的外部 FBInk 版本未知。因此不能断言一定卡在完成等待，也不能将命令返回等同于屏幕物理更新完成。

## 触摸审查：保持现有代码

1. 优先使用可读的 `READING_TOUCH_DEVICE`，否则扫描 sysfs 名称，再回退 `/dev/input/event1`。编号变化且名称仍命中时可自动适应；没有反馈设备的 sysfs 信息，无法判断 5.18.1 是否实际改变了编号或名称。
2. 名称匹配加可读检查并不校验触摸能力；可能命中非实际触摸设备，或回退到可读但不正确的 event1。这是已有风险，本轮不改。
3. Lua 固定读取 16 字节，按两个 32 位时间字段、16 位 type/code、32 位 value 解码；对目标 32 位 ARM little-endian 用户态合理。hard-float 本身不会改变字段大小；64 位用户态通常需要不同布局，实际设备 Lua ABI 未经现场核实。[Linux input_event 定义](https://github.com/torvalds/linux/blob/master/include/uapi/linux/input.h)
4. `assert(io.open(...))` 失败会让 Lua 非零退出，stderr 由 launcher 捕获；短读退出码为 2。Shell 已有 `|| action=exit`，会退出 UI、执行 cleanup，launcher 可能最终仍报告 0，因此需同时查看 stderr / touch log。
5. 打开了错误设备却没有有效事件时，`f:read(16)` 可以持续阻塞，Shell 等待动作，插件无法点击。Lua 不抓取设备、不写 input、不独占触摸，原生系统仍可能使用输入。

## 启动诊断

`/mnt/us/reading-time/dashboard-startup-stage.txt` 保存最新边界，每次打开覆盖：

`first_render_begin` → `first_render_done` → `first_refresh_begin` → `first_refresh_done` → `touch_listener_begin`。

快照含 timestamp、firmware、物理 screen、viewport、touch device path、首次 refresh mode、refresh exit code。`first_render_begin` 包括首屏缓存准备与绘制；`first_render_done` 表示首屏已写入 framebuffer。

- 停在 `first_refresh_begin`：已准备调用刷新，但尚未记录调用返回。
- `first_refresh_done`：调用已经返回；退出码需单独判断，不能保证面板已更新完成。
- `touch_listener_begin`：即将启动 Lua，不保证 input device 已成功打开。结合 `dashboard-touch.log` 的 `interactive watcher started` 和 `last-launch.stderr` 区分打开失败与等待事件。

只写五次小快照；无常驻进程、轮询、额外依赖或重复固件扫描。写入失败忽略，不改变启动结果。非原子覆盖可能在突然断电/进程被强杀时留下不完整快照；下一次打开会覆盖上次信息。早于首屏阶段的依赖失败仍查看现有 `last-launch-status.txt`。

以后失败设备可提供 reading-time 目录中的 `dashboard-startup-stage.txt`、`last-launch-status.txt`、`last-launch.stdout`、`last-launch.stderr`、`dashboard-touch.log` 和 `display-layout.txt`。launcher 的 `dashboard-launch.log` 要等 UI 退出才汇总，本快照可在 UI 卡住时查看。

## 验证与回滚

- `tests/validate_compat.py`：版本识别、窄标记及 export、全部 5.18.x hard-float 门禁、launcher/诊断既有回归。
- `tests/validate_startup_refresh.py`：sh 和 dash 执行生产刷新函数；10 种固件、18 次绘制、区域刷新失败回退与基线命令序列比较；首屏阶段、刷新不返回、非零返回、触摸失败、重复监听及快照写入失败。
- `tests/validate_ui.py`：严格只允许预期 refresh guard 与退出码捕获，继续保护原有触摸发现、UI、数据和 daemon 行为。
- `scripts/validate_all.py`：纳入新增测试，运行既有完整离线检查及安装包逐字节验证；先生成当前源码的测试包，再执行依赖该包的清理测试，避免使用过期包。

2026-10-02 验证结果：全部 16 项离线检查通过。新增刷新测试完成 40 组基线命令序列对比、30 组启动/失败场景及两种 shell 的诊断写入失败检查。首次全套运行在清理测试发现旧包与新源码不一致；修正构建顺序后保留已通过的前 11 项，重新执行余下 5 项，全部通过。完整输出见 `build/validation/fw5181-suite.log`。未进行真机测试。

回滚运行改动只需恢复 `compat/detect_env.sh` 与 `阅读记录-optimized.sh` 两个源文件，并使用原有安装/升级方式部署。测试和本文档不进入运行依赖。

未知风险：nonflashing GC16 的实际残影和驱动行为需新失败设备验证；周期清屏、退出刷新及旧版 fallback 保留原策略；如果真实问题来自触摸设备选择、Lua ABI 或原生窗口管理，本补丁不会解决。若界面可见但仍无法点击，应依据上述阶段和既有日志单独定位触摸路径。

# test12：安装报告保存与书库条目修复

本候选基于已发布的 test11，仅交付本地 ZIP。产品身份为 `9.8.1-5.20-vera-test12`，既有 runtime 路径 `9.8.1-5.20-vera-test1` 保留；不修改 GitHub Release、5.19 附件或 KS。

## 已确认的问题与证据边界

用户提供的照片显示书库多出安装结果及中英文诊断文档，没有错误正文。后续确认没有明确失败提示；设备属于他人，无法确认插件是否可打开，也没有可用设备日志。因此不能将该照片作为安装或启动失败的确证。

对比 SHA-256 固定的 test10、test11 原包，两者 bootstrap 安装事务相同，仅版本、build_id 和 payload 校验值不同；诊断、服务、生命周期及旧迁移逻辑逐字节相同。两版都在 `documents` 写安装结果；安装核心失败时还会自动导出两份诊断 TXT。这些文件可能被 Kindle 扫描成书库条目。

另发现两版 ZIP 内安装数据的大小与时间戳相同。test12 使用实际构建 UTC 时间作为两个 ZIP 成员的时间戳，并在 BUILD-INFO 中记录 build_epoch；构建工具支持 SOURCE_DATE_EPOCH 固定时间以复现产物。此项降低覆盖复制时误跳过旧文件的风险，不作为照片中问题的已证实原因。

## 修改后的行为

- 安装开始即写入 `reading-time/install-logs/reading-records-v4-install-result.txt` 和同目录的 `reading-records-v4-install.log`。结果字段、失败退出码和原子发布保留，清理安装文件也不会删除这些证据。
- 安装失败的自动诊断写入该目录的 `last-install-diagnostic.txt`，不受继承的手动导出路径影响。自动启动诊断继续使用原内部位置；明确请求的手动诊断仍保留原导出接口。
- 升级将四个已知旧报告名与其内容结构一起核对，归档到内部 `legacy/reports.进程号/`。复制、逐字节比较并重新核对源文件校验和后才移除原文件；未知内容、链接、目录、复制失败、归档位置被占用及校验失败均保留原文件。此归档独立于 runtime 回滚，证据不会随回滚丢失。
- 中文报告名使用精确字符串比较，避开部分 dash 在函数内匹配非 ASCII case 模式的兼容问题；sh 与 dash 均执行报告保护和归档检查。
- 报告目录或输出路径被链接、目录或其他不兼容内容占用时停止写入；退出清理也不会通过拒绝的路径创建文件。
- 保留大小及校验和检查，增加 payload 产品身份、build_id 与 bootstrap 的一致性检查。混用旧安装数据仍明确失败，不能被误记为安装成功。

彩色封面 ARM 程序、蓝牙输入 ARM 程序、主 UI、计时实现、FBInk 实际命令选择和 GC16 策略均保留 test11 字节。安装事务、rollback、repair、防混装和历史、图片、配置保护保持有效。

## 安装与核验

ZIP 顶层只有 `reading-records-v4-install.sh` 与 `阅读记录安装数据.tar`。只解压外层一次，将两文件一起复制到 Kindle documents，按既有步骤原地安装，无需先卸载。

完整结果及 SHA-256 见 [test12 核验报告](releases/9.8.1-5.20-vera-test12-verification.json)。独立开发核验命令为 `python scripts/verify_install_test12.py`，只读且不会重新构建。

离线场景覆盖真实 test10/test11 原包升级、清理后升级、重复安装、故障回滚、报告归档与路径保护，以及色彩、UI、蓝牙计时和服务回归。离线结果不代表这台照片中的设备或其他设备已经通过实机验收；普通用户无需运行核验命令、选择 runtime 或承担兼容性排查。

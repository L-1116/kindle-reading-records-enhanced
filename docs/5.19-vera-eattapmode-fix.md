# 9.7.6-5.19-vera：只写 LIPC 属性启动修复

## 真机发现与根因

2026-10-08 收到用户首轮真机反馈：KPW6 / firmware 5.19.6 / Véra 已确认安装 SUCCESS、verified activation completed、正式图标和清理入口正常；打开阅读记录闪白后返回主页。日志停在 `orientation_original=U geometry=1272x1696` 和 `ERROR: 无法保存触摸状态`。

冻结起点为 `df5fd1e128d6a943435ea0ee8426b8f9f166b250`。该启动器强制用 `lipc-get-prop` 保存 `eatTapMode`，读取失败即退出，尚未启动 UI。[winmgr 属性表](https://kindlemodding.org/kindle-apps-and-services/com.lab126.winmgr.html) 和 [设备 LIPC 属性转储](https://gist.github.com/notmarek/4fd16a6e8df4b6a0e60110c926067c88) 都将其列为 Int / w；`orientationLock` 则为 rw。这与用户日志相符。离线以读取必然返回非零、无原值输出的模拟器，在 sh/dash 均重现同一错误及 UI 未进入。

9.7.5 基线 `e41707492b985284d77e0ec5ec5ceffe98209a89` 没有独立 `launch.sh`；`阅读记录-optimized.sh` 和旧渲染入口 `阅读记录.sh` 都在进入和退出时尽力写 `eatTapMode 0`，没有读取、没有保存原值。这是旧版设置行为，不是恢复已知原状态。不能沿用“原状态可读并精确恢复”的说法。

旧 `normal_fixture.py` 默认生成数值文件且允许 `lipc-get-prop` 返回该文件内容，把只写属性当成 rw；因此上一轮离线通过漏掉了真机启动阻断。历史 pre-hardware/final-freeze 报告中有关“恢复原 eatTapMode”的断言由本记录纠正，历史文件保留作为审计记录。

## 最小修复与不变部分

生产 payload 仅修改 `native-reading-time-package/launch.sh`：删除 `eatTapMode` 读取、临时写入、原值变量、pending 标记和退出恢复命令。没有伪造原值 0，也没有尽力写 0 的新 fallback。两个原有 Lua 监听器通过 `io.open(device, "rb")` 只读 evdev，未使用 EVIOCGRAB，也未调用该 LIPC 属性；保留它们的原始字节。基于这一路径选择完全不修改 `eatTapMode`；目标机器上的触摸行为仍需真机证实。

`orientationLock` 的保存、临时竖屏、等待 geometry、Library 后恢复原方向，以及 `preventScreenSaver` 的读取、校验、修改前 pending、恢复实际原值均保留。退出顺序仍为 owned UI/reader 终止并 wait → 恢复实际 preventScreenSaver → 打开 Library → 必要时等待并恢复原 orientationLock → 释放锁。会话锁、INT/TERM/HUP、fork/PID 交接和幂等清理保持不变。

未修改统计、封面、Lua 渲染、触摸坐标、daemon、TSV 或历史格式。安装事务、rollback、repair、防混装与白名单清理保持原实现。新 ZIP 名称使用 vera；内部 `9.7.6-5.19-normal` release ID 和安装两文件名不变，直接执行同版本 repair，保留 reading-time.tsv、备份、历史、配置、封面和统计缓存。

## 验证覆盖

完整 suite 包括 UI/统计/日期/周期/书籍/封面、安装包构建、历史字节审计、安装/回滚/升级、runtime 故障与信号、pre-hardware 及 final-freeze 检查。
